# 경매 3조건 퍼널 스크리닝 (auction-screening)

"지역 전체에서 조건 통과 물건만 남기는" 깔때기(funnel). 각 단계가 **점점 줄여** 마지막엔 소수만 남긴다.
개별 스킬(court-search·apt-value·rights-analysis·profit-analysis·location-metrics·report-builder)을
**하드필터 순서로 엮은 워크플로**다. 실행체는 `webapp/`(로컬 Flask 앱).

## 퍼널 3단계 (줄어드는 순서)

| 단계 | 조건 | 판정 방법 | 담당 |
|---|---|---|---|
| **1조건** | 아파트 · 유찰횟수 · 전용면적 · 최저매각가 | 경매 검색 API 서버필터 | court-search `collect_api.py` |
| **2조건** | 세대수 · 사용승인연도 · **실거래량(매도 환금성)** | 공동주택 API + 실거래 DuckDB | apt-value + realprice 캐시 |
| **3조건** | 매각물건명세서·현황조사·감정평가·문건송달 → 권리리스크 | 인수보증금·대항력 판정 | rights-analysis `analyze_case.py` |
| **최종** | 통과분 비교분석 | 입지 6축·실거래 시세·수익률 | location-metrics + profit + report-builder |

> **왜 순서가 중요한가**: 뒤로 갈수록 느리다(3조건 권리는 물건당 Playwright ~40초). 그래서
> **싸고 빠른 필터(1·2조건)로 먼저 최대한 줄이고**, 느린 3조건은 **저감율 상위 N건만** 돌린다.

## 🔑 2조건 — 매도 환금성(실거래량)이 핵심

세대수·연식만으로는 부족하다. **"팔 수 있는 물건인가"가 제일 중요**하고, 이는 **실거래량**으로 본다.

- **규칙**: 해당 단지·해당 평형(±3㎡)의 **월평균 실거래 ≥ 세대수/500 × N** (N=500세대당 월 최소 건수, 기본 1).
  - 500세대 → 월 1건, 1000세대 → 월 2건, 2320세대 → 월 4.6건 필요(세대수 비례).
  - **미달이면 탈락** — 대단지·신축이라도 거래가 없으면 매도가 안 된다.
- 실측 예: 이안 평택안중역(610세대·2024)은 최근 1년 실거래 3건(월 0.25) → **환금성 부족 탈락**.
  안성 원곡오투그란데(797세대)는 43건(월 3.58) → 통과.
- 실거래 매칭은 **단지명 정규화 후 부분일치**(공백·접두 차이 흡수: '원곡 제일 오투그란데' ↔ '원곡제일오투그란데').
- 세대수·연식은 공동주택 기본정보 API. **화성시 등 목록 API 공백** 단지는 매칭 불가 → 별도 확인(apt-value 참조).

## 🔑 3조건 — 권리 판정은 구조화 필드로 (오탐 금지)

- 인수 금액은 analyze_case의 **`report.투자분석.인수보증금`(정수)** 을 근거로 쓴다.
- **HUG 대항력포기**는 **매각물건명세서 비고 원문(`ndstrcRghCtt`)에 있을 때만** 인정.
  ⚠️ **JSON 전체 텍스트에서 '대항력'+'포기'를 찾으면 안 된다** — 문건송달·인근사례에 걸려
  **인수위험을 안전으로 오판**한다(실측: 안성 롯데캐슬 인수 4억을 "안전"으로 잘못 통과시킨 버그).
- 판정 우선순위: 인수보증금==0 → 안전 · 비고 대항력포기 → 안전(HUG) · 인수보증금>0 → 인수위험 ·
  인수위험플래그만 → 인수위험(금액미상). 상세는 rights-analysis 스킬.

## 실행 A — 로컬 웹앱 (권장)

```bash
pip install flask duckdb "PublicDataReader>=1.1.1" python-dotenv pandas requests playwright
python -m playwright install chromium
python webapp/app.py           # → http://127.0.0.1:5000
```
폼에 조건 입력(지역=서울/경기, 유찰·면적·최저가, 세대수·사용승인연도, **환금성 500세대당 월 N건**,
권리 상위 N건) → "분석 시작" → 퍼널 카운트(1→2→3) 실시간 + 최종 비교표.
- 첫 실행은 실거래 DuckDB 캐시(`webapp/realprice_cache.duckdb`) 채우느라 느리고 이후 빨라진다.
- 도(道) 전역은 관할 법원 여러 개를 자동 순회(court-search의 지원 단축명 규칙 적용).

## 실행 B — 개별 스킬 수동 조합

1. **1조건**: court-search `collect_api.py` (도 전역이면 관할 법원 각각 → CSV 합침·dedup).
2. **2조건**: 각 물건 단지명→공동주택 API로 세대수·준공 → 실거래로 **평형별 월거래량** 계산 →
   세대수·연식·환금성 하드필터. (대량이면 공동주택 **시도목록 1회 캐시** 후 로컬 매칭 — apt-value 참조.)
3. **3조건**: 저감율 상위 N건만 rights-analysis `analyze_case.py` → 인수보증금·HUG 판정.
4. **최종**: 통과분에 location-metrics(입지 4축)·profit-analysis(8대비용 수익)·report-builder(비교 HTML).

## 결과 전달

퍼널 숫자를 먼저 말한다: **"1조건 N → 2조건 M → 최종 K건"**. 그다음 통과 K건만 표로
(단지·세대·연식·**월거래량**·시세·세전차익·ROI·입지등급·권리). 탈락 사유(환금성 부족·인수위험 등)를
물건별로 남기고, 시세·수익률은 "추정 — 입찰 전 등기부·전입세대열람·현장 검증 필수"를 붙인다.
